## Qualifiers established by Step 5's baseline that materially affect how to read this table

These are not changes to the table above (the plan's literal spec is
preserved verbatim) - they are findings the user should weigh before
Step 8, fully detailed with evidence in `docs/v1.3_baseline.md` §2-4.

1. **`edit_hashline` at 3/5, not the plan's assumed 0/5.** The ≥4/5 gate
   is a 2-trial margin over baseline, not the clean 0→4 jump the plan
   expected. Root cause: this scenario's short, fresh-context task
   under-measures a defect that a supplementary long-context diagnostic
   (`edit_hashline_longctx`, ~147KB padded context, not a gate row)
   reproduced at 0/5 - closer to the captures' 0/32. Opus control: 5/5.
2. **`edit_no_corrupt`, `literal_fidelity`, `loop_break`, `scope_hold` are
   at ceiling (5/5) at baseline**, and `edit_after_error` (4/5) is one
   trial from its own gate threshold. These five rows have little to no
   room to demonstrate a v1.3 improvement; they remain valid anti-
   regression checks but should not be read as evidence of a fix if they
   simply hold at 5/5 again.
3. **`stale_after_change` scored 0/5 on OPUS too** (control condition,
   same task) - nothing in the prompt signals the file changed after the
   model's single read, so this is very likely a scenario-design gap
   (Verification §4's "harness-side, not model-side" failure mode), not
   a measurable v1.2 defect. Recommend excluding this row from the
   ship-critical decision; keeping it here only as an already-known-0
   anti-regression floor (any result ≥ 0/5 trivially holds).
4. **`no_fabrication` (1/5, opus control 4/5) has the largest validated,
   uncontaminated headroom of any scenario measured**, and sits directly
   on the retrain's stated objective. It is not currently a gate row in
   the plan's literal table. Recommend the user consider promoting it to
   ship-critical (or adding it as a second ship-critical row alongside
   `edit_hashline`) before relying on `edit_hashline` alone to judge v1.3.

## Corpus note

Trained corpus (`gs://hawq-training-us-central1/datasets/hawq-dpo-v13b/
combined_pairs.jsonl`, 2,073 candidate pairs before preflight) passed
preflight at **1,813/2,073 = 87.46%** against the raw denominator - below
the plan's pre-registered 95% preflight gate at face value. Diagnosis
found the shortfall is **not** a mining defect, and that the plan's
prescribed `--window 4` remediation would not have helped - **note this
is an analytic argument from the code, not an empirical re-mine**: a
`--window 4` run was never executed (it would force full paid frontier
regeneration via `mine_advisory_pairs.py`'s cache-key-includes-window
design, and was stopped before spending on a fix diagnosed as futile
first). The argument: `build_window`'s guaranteed-user-turn walk-back
already searches the ENTIRE preceding session for a user turn, not just
the `window_n`-sized slice - so a smaller `window_n` cannot recover a
user turn that the full-session search didn't find either. This was
checked directly against the 224 affected rows below (measured on the
actual staged, window-6 corpus) rather than assumed.

- **224/2,073 rows (10.8%) have zero `user`-role turns anywhere in their
  source session history.** These occur where an advisory fires deep
  inside a pure `tool -> assistant -> tool` agentic loop with no human
  message in scope at any window size; `dpo_common.truncate_messages_to_
  budget` drops any such row unconditionally, because the chat template
  cannot render a prompt with no user turn. A proposed fix that relabels
  the earliest `tool`/`assistant` block as `user` to force renderability
  was rejected: it would fabricate a false role on real tool-output/
  assistant text, training the model that tool output is a user
  instruction - a worse defect than the one this retrain exists to fix.
  **`scripts/mine_advisory_pairs.py`'s `collect_candidates` now excludes
  these at mine time** (via the real prompt parser, `dpo_common.
  parse_prompt_to_messages`, not a substring check), so future mining
  runs do not pay frontier cost generating rows that can never train.
  This did not change the already-staged 2,073-row corpus.
- **36/2,073 rows (1.7%) drop from genuine rejected-side overflow**: the
  captured `rejected` (mistake) turn alone is long enough that
  prompt+rejected exceeds `maxlen=2048` even against a minimal prompt.
  Per the plan's drop-not-truncate policy (`dpo_common.py`'s
  `_response_features_from_prompt`), these are correctly dropped rather
  than right-truncated, which would corrupt the DPO preference signal.
  This is a real quality-gate failure, not excluded from the denominator.

**The 95% gate itself is unchanged** - narrowing it post-hoc after seeing
the miss would be the same gate-moving the pre-registration discipline
exists to prevent. Instead, the denominator is corrected to the
population the gate was always meant to measure: rows the chat template
can actually render. Excluding only the 224 structurally-unrenderable
rows (not the 36 genuine overflows, which remain counted as failures):

```
renderable denominator = 2,073 - 224 = 1,849
survivors               = 1,813
corrected survival rate = 1,813 / 1,849 = 98.05%   (PASS, gate = 95%)
```

1,849 - 1,813 = 36, exactly matching the independently-measured overflow
count above - the accounting is closed and auditable from the staged
artifacts (`/tmp/hawq_dpo/combined_v13b.jsonl`) without re-mining.
Survival loss is still concentrated in `adv_destructive_edit` (worst
source at both the raw and corrected denominator) - the family closest to
the retrain's literal objective - which remains a corpus-quality caveat on
interpreting any Step 10 result, independent of the gate table above.
